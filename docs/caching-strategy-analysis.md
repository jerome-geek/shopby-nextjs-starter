# 캐싱 및 렌더링 전략 분석 (Caching Strategy Analysis)

본 문서는 현재 프로젝트의 페이지별 렌더링 방식과 캐싱 전략을 분석하고, 향후 최적화 방향을 제안하기 위해 작성되었습니다.

## 1. 현재 페이지별 렌더링 현황

| 페이지      | 경로             | 현재 방식   | 권장 방식 (To-Be) | 비고                                     |
| :---------- | :--------------- | :---------- | :---------------- | :--------------------------------------- |
| 메인 홈     | `/`              | Static (○)  | **ISR (●)**       | 주요 데이터(배너 등) SEO 최적화 필요     |
| 상품 상세   | `/products/[id]` | **SSR (λ)** | **ISR (●)**       | On-Demand Revalidation 연동 시 속도 향상 |
| 레시피 상세 | `/recipes/[sno]` | **ISR (●)** | ISR (●)           | 현재 최적화 상태 (6H 주기 + 수동 갱신)   |
| 쇼핑 가이드 | `/shop/[slug]`   | SSR (λ)     | **SSG (●)**       | 고정된 카테고리이므로 SSR 불필요         |
| 마이페이지  | `/mypage/*`      | Static (○)  | Static (○)        | 클라이언트 사이드 데이터 fetching 유지   |

## 2. On-Demand Revalidation (수동 갱신) 도입

데이터 변경 시 수동으로 캐시를 무효화하기 위한 API 엔드포인트가 구축되었습니다.

- **API 주소**: `/api/revalidate`
- **인증 방식**: HTTP Header (`x-revalidate-token`) 또는 Query Parameter (`secret`)
- **대상**: ISR이 적용된 모든 페이지 (레시피 상세 등)

## 3. 어드민(S3) 연동 및 보안 고려사항

### 현황

어드민 페이지가 S3 정적 호스팅으로 배포될 예정이므로, 브라우저의 네트워크 탭에서 인증 토큰이 노출될 수 있는 위험이 있습니다.

### 대응 방안

1. **Server-to-Server 호출 (권장)**: 어드민이 사용하는 백엔드 API 서버가 존재한다면, 백엔드에서 Next.js API를 호출하여 토큰을 은닉합니다.
2. **Referrer 제한**: Next.js API 서버에서 특정 어드민 도메인에서 온 요청만 수락하도록 CORS 설정을 강화합니다.
3. **리스크 수용**: 해당 API는 페이지 가시성을 업데이트할 뿐 데이터 파괴 능력이 없으므로, Rate Limit(회당 요청 제한) 설정 등으로 남용을 방지하며 사용합니다.
