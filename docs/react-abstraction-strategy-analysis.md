# 리액트 추상화 전략 분석 가이드: 정책과 메커니즘의 분리

본 문서는 리액트 컴포넌트 설계 시 "언제, 어떤 추상화를 적용해야 하는가"에 대한 팀의 기술적 가이드라인을 정의합니다. [최기환 님의 아티클](https://velog.io/@koreanthuglife/%EB%A6%AC%EC%95%A1%ED%8A%B8%EC%97%90%EC%84%9C-%EC%96%B8%EC%A0%9C-%EC%96%B4%EB%96%A4-%EC%B6%94%EC%83%81%ED%99%94-%EC%A0%84%EB%9E%B5%EC%9D%84-%EC%82%AC%EC%9A%A9%ED%95%B4%EC%95%BC-%ED%95%A0%EA%B9%8C)을 바탕으로 우리 프로젝트의 환경에 맞춰 구성되었습니다.

---

## 1. 핵심 철학: 정책(Policy) vs 메커니즘(Mechanism)

설계의 핵심은 **"변경 확률이 높은 영역"**과 **"낮은 영역"**을 분리하는 것입니다.

| 구분 | 정의 | 리액트에서의 역할 | 추상화 방향 |
| :--- | :--- | :--- | :--- |
| **메커니즘 (Mechanism)** | **어떻게(How)** 동작하는가. 불변하거나 변화가 적은 시스템 하부 구조. | 데이터 패칭 흐름, 순회 로직, 상태 업데이트 방식 | **내부 캡슐화** |
| **정책 (Policy)** | **무엇을(What)** 원하는가. 비즈니스 요구사항에 따라 자주 변하는 규칙. | UI 스타일, 구체적인 렌더링 결과, 버튼 클릭 동작 | **외부 위임 (Open)** |

### ✅ "언제 추상화해야 하는가?"
- 단순히 코드가 길어질 때가 아니라, **서로 다른 맥락(Context)의 정책들이 한 곳에 뒤엉켜 강한 결합이 발생할 때**입니다.

---

## 2. 추상화 도구 선택 기준 (Hook vs Component)

| 도구 | 주된 추상화 대상 | 특징 |
| :--- | :--- | :--- |
| **커스텀 훅 (Hook)** | **행동(Behavior)과 상태(State)** | 데이터가 컴포넌트 전체 스코프에 병합됨. 전체 라이프사이클에 영향. |
| **컴포넌트 (Component)** | **구조(Structure)와 렌더링(Rendering)** | 데이터 범위를 국소화(Render Props)하고 렌더링 영향 범위를 제어. |

> **Insight**: UI와 강하게 결합된 기능(예: 모달, 리스트)은 컴포넌트로 묶어 **응집도**를 높이는 것이 선언적 프로그래밍에 유리합니다.

---

## 3. 컴포넌트 구현 전략: Container vs Content

### ⚪ 흐름을 제어하는 컨테이너 (Container) -> "열어야 한다 (Open)"
- **역할**: "무엇"을 보여줄지는 관심 없고, "어떻게" 배치하고 흐르게 할지만 담당.
- **예시**: `List`, `Layout`, `ModalWrapper`, `FetchBoundary`
- **전략**: **Render Props**나 **Children** 패턴을 사용하여 내부 내용물 렌더링을 외부로 위임(IoC)합니다.

### ⚫ 정보를 표현하는 콘텐츠 (Content) -> "닫아야 한다 (Close)"
- **역할**: "무엇"인지를 명확히 시각화하여 보여주는 말단.
- **예시**: `ProductCard`, `UserItem`, `Button`
- **전략**: **캡슐화(Encapsulation)**를 통해 디자인 일관성을 유지합니다. Props로 데이터만 받고 내부 구현은 숨깁니다.

---

## 4. 프로젝트 적용 가이드 (예: BestProductsPage)

우리 프로젝트의 실제 페이지 리팩토링 시 아래와 같은 계층 구조를 지향합니다.

1.  **State Layer (Hook)**: `useQueryStates` 등을 통해 URL 상태와 비즈니스 파라미터 계산 담당 (`useBestProductParams`).
2.  **Mechanism Layer (Mechanism Component)**: PC/모바일 환경에 따른 페칭 방식 분기 처리 담당 (`BestProductListContainer`).
3.  **Policy Layer (Content Component)**: 실제 디자인 시스템이 적용된 말단 컴포넌트 (`ProductCard`).
4.  **Coordinator (Page)**: 위 요소들을 배치하여 하나의 페이지 정체성을 완성.

---

## 5. 결론
추상화의 최종 목표는 **"현재 우리 시스템에서 무엇이 더 자주 변하는가?"**에 답하는 것입니다. 변화의 속도가 다른 코드들을 분리함으로써, 수정을 최소화하고 확장이 용이한 구조를 유지합니다.
